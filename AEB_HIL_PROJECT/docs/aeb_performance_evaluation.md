# AEB Performance Evaluation Framework

## 1. Executive Summary & Purpose

This document formally establishes the **Autonomous Emergency Braking (AEB) Performance Evaluation Framework** for the project. 

The purpose of this framework is to provide a standardized, mathematically grounded, and transparent methodology for evaluating the closed-loop performance of the AEB system across simulation, sensitivity studies, and future Hardware-in-the-Loop (HIL) testing.

### Core Scientific Guidelines

> [!IMPORTANT]
> - **Software Simulation Context:** This evaluation framework currently assesses numerical results generated by Python simulation models. It does **not** constitute real-vehicle validation, Hardware-in-the-Loop (HIL) certification, or regulatory compliance.
> - **Distinction Between Observation and Requirement:**
>   - **WHAT WE MEASURE:** The raw physical or algorithmic state history recorded during a test run.
>   - **WHAT WE OBSERVE:** The empirical outcomes produced by the current software model under specific test scenarios (e.g., zero collisions, specific minimum clearance distances).
>   - **WHAT CONSTITUTES PASS/FAIL:** A validated threshold derived from engineering requirements, vehicle specifications, or standardized test protocols. An observation that "collision did not occur" in simulation is **not** sufficient proof of safety.
> - **Structural Reversal Patterns vs. Physical Chattering:** The metric `triplet_reversal_count` measures the **"Number of 3-sample sliding FSM reversal patterns"**. It is a software-level indicator of boundary switching frequency; it does **not** represent physical mechanical chattering, vehicle instability, or unsafe events.

## 4. Detailed Profiles for Each Metric

### 4.1 Collision Status (`collision_status`)
- **Mathematical Definition:**
  $$\text{collision\_status} = \exists k \in [0, N-1] \text{ s.t. } d_{\text{raw}}[k] \le 0.0 \land v_{\text{rel}}[k] > 10^{-4}\text{ m/s}$$
- **Unit:** Boolean (`True` / `False`)
- **Category:** Safety
- **Physical Meaning:** Detects physical contact between the ego vehicle front bumper and target vehicle rear bumper while closing speed exists.
- **Calculation in Software:** Evaluated dynamically over the trajectory in `PerformanceEvaluator.evaluate()`. Unclamped raw distance is checked against 0.0 with positive closing speed to avoid false positives at rest.
- **Distinction:**
  - *What We Measure:* Unclamped longitudinal displacement and relative velocity.
  - *What We Observed:* `collision_status = False` in 100% of tested runs (1440/1440 runs).
  - *What Constitutes Pass/Fail:* Pass requires `collision_status == False`. This is a necessary safety requirement, but not sufficient on its own.
- **Threshold Status:** Established (`False`). Source: Test Protocol & System Safety Goal.

---

### 4.2 Minimum Separation Distance (`minimum_distance`)
- **Mathematical Definition:**
  $$d_{\min} = \min_{k \in [0, N-1]} d[k]$$
- **Unit:** meters (m)
- **Category:** Safety
- **Physical Meaning:** The closest proximity reached between ego and target vehicles throughout the maneuver.
- **Calculation in Software:** Minimum value of physical distance history `[s.distance for s in result.samples]`.
- **Distinction:**
  - *What We Measure:* Bumper-to-bumper distance profile.
  - *What We Observed:* $0.8250\text{ m} \le d_{\min} \le 4.7260\text{ m}$ across combined impairment experiments.
  - *What Constitutes Pass/Fail:* Must exceed a designated positive clearance buffer $d_{\text{safe}}$ (e.g., $d_{\min} \ge d_{\text{buffer}}$).
- **Threshold Status:** **TBD**. Currently ungrounded. Requires platform-specific tolerance margins and measurement uncertainty analysis.
- **Threshold Source Needed:** Vehicle/platform specification & Safety margin standard.

---

### 4.3 AEB Activation Time (`aeb_activation_time`)
- **Mathematical Definition:**
  $$t_{\text{act}} = \min \{ t_k \mid a_{\text{cmd}}[k] < 0.0 \}$$
- **Unit:** seconds (s)
- **Category:** Timeliness
- **Physical Meaning:** The exact elapsed simulation time at which the FSM exits non-braking states (`SAFE`, `WARNING`) and issues an active deceleration command (`AEB_LEVEL_1`, `2`, or `3`).
- **Calculation in Software:** Timestamp of first `SimulationSample` where `desired_deceleration < 0.0` in `PerformanceEvaluator.evaluate()`. `None` if braking never triggers.
- **Distinction:**
  - *What We Measure:* Time from simulation origin $t=0$ to active braking command.
  - *What We Observed:* $0.00$ s for CCR and CCRm (since initial distance/speed places vehicles within threat envelope immediately); $1.85\text{--}2.00$ s for CCRb (delayed by target deceleration onset and sensor latency).
  - *What Constitutes Pass/Fail:* Must fall within an allowable time window relative to threat emergence ($t_{\text{target\_brake}} + \Delta t_{\text{budget}}$).
- **Threshold Status:** **TBD**.
- **Threshold Source Needed:** Threat horizon definition & Test protocol.

---

### 4.4 Time-To-Collision at Activation (`ttc_at_activation`)
- **Mathematical Definition:**
  $$\text{TTC}_{\text{act}} = \frac{d[k_{\text{act}}]}{v_{\text{rel}}[k_{\text{act}}]}$$
- **Unit:** seconds (s)
- **Category:** Timeliness
- **Physical Meaning:** The projected time remaining before impact at the instant active braking intervention is initiated, assuming constant relative velocity.
- **Calculation in Software:** Ratio of measured/true distance to relative velocity recorded at sample index $k_{\text{act}}$.
- **Distinction:**
  - *What We Measure:* Kinematic ratio $d / v_{\text{rel}}$ at $t_{\text{act}}$.
  - *What We Observed:* $2.00$ s in CCR (triggered at LEVEL_2 threshold $2.25$ s), $2.50$ s in CCRm (triggered at LEVEL_1 threshold $3.00$ s), $2.97\text{--}3.00$ s in CCRb.
  - *What Constitutes Pass/Fail:* Braking must not trigger prematurely when TTC is large (false intervention avoidance) nor delay past critical stopping limits.
- **Threshold Status:** **TBD** (Design criteria: warning at $\le 4.0$ s, braking escalation at $\le 3.0$ s, $\le 2.25$ s, $\le 1.75$ s; requires formal validation).
- **Threshold Source Needed:** Human factors literature & Standardized AEB test protocols.

---

### 4.5 Maximum Commanded Braking Deceleration (`max_braking_deceleration`)
- **Mathematical Definition:**
  $$a_{\text{cmd,max}} = \max_{k} |a_{\text{cmd}}[k]|$$
- **Unit:** meters per second squared (m/s²)
- **Category:** Braking Effectiveness
- **Physical Meaning:** The maximum deceleration demand output by the controller FSM.
- **Calculation in Software:** Absolute value of the minimum commanded acceleration across all samples.
- **Distinction:**
  - *What We Measure:* Controller output variable `desired_deceleration`.
  - *What We Observed:* $6.00$ m/s² in CCR, $4.00$ m/s² in CCRm and CCRb.
  - *What Constitutes Pass/Fail:* Commanded deceleration must not exceed the vehicle's safe actuator limits or tire adhesion capability.
- **Threshold Status:** **TBD** (Controller ceiling is $6.00$ m/s²).
- **Threshold Source Needed:** Vehicle platform actuator authority limit.

---

### 4.6 Maximum Actual Braking Deceleration (`max_actual_deceleration`)
- **Mathematical Definition:**
  $$a_{\text{act,max}} = \max_{k} |a_{\text{actual}}[k]|$$
- **Unit:** meters per second squared (m/s²)
- **Category:** Braking Effectiveness
- **Physical Meaning:** The maximum deceleration physically delivered at the vehicle chassis by the brake actuator dynamics.
- **Calculation in Software:** Absolute value of minimum actual acceleration in `PerformanceEvaluator.evaluate()`.
- **Distinction:**
  - *What We Measure:* Plant state `actual_deceleration`.
  - *What We Observed:* Matches $a_{\text{cmd,max}}$ under ideal $\tau=0.0$ s; reaches $5.8\text{--}6.0$ m/s² under lag $\tau \le 0.30$ s.
  - *What Constitutes Pass/Fail:* Must achieve minimum required braking force without exceeding physical adhesion limits ($\mu \cdot g$).
- **Threshold Status:** **TBD**.
- **Threshold Source Needed:** Vehicle specification (tire-road friction $\mu$, hydraulic pressure limit).

---

### 4.7 90-Percent Braking Response Time (`ninety_percent_braking_response_time`)
- **Mathematical Definition:**
  $$t_{\text{resp,90\%}} = t_{90\%} - t_{\text{act}} \quad \text{where } t_{90\%} = \min \{ t_k \ge t_{\text{act}} \mid |a_{\text{actual}}[k]| \ge 0.90 |a_{\text{cmd}}[k_{\text{act}}]| \}$$
- **Unit:** seconds (s)
- **Category:** Timeliness
- **Physical Meaning:** The rise time required for the physical brake actuator to build 90% of the initial commanded step deceleration.
- **Calculation in Software:** Difference between timestamp reaching 90% threshold and activation timestamp in `PerformanceEvaluator.evaluate()`.
- **Distinction:**
  - *What We Measure:* Time interval between command step and plant deceleration rise.
  - *What We Observed:* $0.00$ s for $\tau=0.0$ s; $0.20$ s for $\tau=0.10$ s; $0.35\text{--}0.45$ s for $\tau=0.20$ s; $0.35\text{--}0.60$ s for $\tau=0.30$ s.
  - *What Constitutes Pass/Fail:* Response time must satisfy maximum allowable hydraulic build-up delay (typically $< 0.30\text{--}0.40$ s in commercial brake systems).
- **Threshold Status:** **TBD**.
- **Threshold Source Needed:** Brake actuator hardware specification (ISO 22839 / supplier datasheet).

---

### 4.8 Stopping Time (`stopping_time`)
- **Mathematical Definition:**
  $$t_{\text{stop}} = \min \{ t_k \mid |v_{\text{ego}}[k]| \le 10^{-5}\text{ m/s} \}$$
- **Unit:** seconds (s)
- **Category:** Braking Effectiveness
- **Physical Meaning:** Total elapsed simulation time from scenario start until ego vehicle achieves complete standstill.
- **Calculation in Software:** Timestamp of first sample where `math.isclose(s.ego_speed, 0.0, abs_tol=1e-5)`. `None` if vehicle does not achieve zero speed.
- **Distinction:**
  - *What We Measure:* Standstill timestamp.
  - *What We Observed:* $2.50\text{--}4.00$ s in stopped scenarios; `None` in CCRm when ego vehicle matches target speed without stopping.
  - *What Constitutes Pass/Fail:* Must stop within scenario timeout limits.
- **Threshold Status:** **TBD**.
- **Threshold Source Needed:** Test protocol definition.

---

### 4.9 Stopping Distance (`stopping_distance`)
- **Mathematical Definition:**
  $$d_{\text{stop}} = \sum_{k=0}^{N_{\text{stop}}-1} v_{\text{ego}}[k] \Delta t[k]$$
- **Unit:** meters (m)
- **Category:** Braking Effectiveness
- **Physical Meaning:** The cumulative ground distance traversed by the ego vehicle from scenario start until full stop.
- **Calculation in Software:** Numerical integration of ego ground speed over sample timestamps up to `first_stop`.
- **Distinction:**
  - *What We Measure:* Longitudinal travel distance to standstill.
  - *What We Observed:* $4.0\text{--}4.7$ m from braking onset; overall scenario distance depends on pre-braking coast.
  - *What Constitutes Pass/Fail:* Must be less than initial separation distance minus safe clearance ($d_{\text{stop}} \le d_0 - d_{\text{buffer}}$).
- **Threshold Status:** **TBD**.
- **Threshold Source Needed:** Kinematic vehicle stopping capability.

---

### 4.10 Vehicle Stop Status (`vehicle_stop_status`)
- **Mathematical Definition:**
  $$\text{stop\_status} = \begin{cases} \text{"STOPPED"}, & \text{if } \exists k \text{ s.t. } |v_{\text{ego}}[k]| \le 10^{-5}\text{ m/s} \\ \text{"NOT\_STOPPED"}, & \text{otherwise} \end{cases}$$
- **Unit:** Categorical string (`"STOPPED"` / `"NOT_STOPPED"`)
- **Category:** Safety
- **Physical Meaning:** Categorical confirmation whether the ego vehicle came to a complete halt.
- **Calculation in Software:** Evaluated dynamically in `PerformanceEvaluator.evaluate()`.
- **Distinction:**
  - *What We Measure:* Velocity convergence to zero.
  - *What We Observed:* `"STOPPED"` in CCR with residual deceleration; `"NOT_STOPPED"` in scenarios where low residual speed ($0.2$ m/s) persists or in CCRm where target maintains motion ($5.0$ m/s).
  - *What Constitutes Pass/Fail:* Mandatory `"STOPPED"` in stationary obstacle scenarios (CCR); `"NOT_STOPPED"` is acceptable in moving target scenarios (CCRm) provided threat is mitigated.
- **Threshold Status:** **TBD**.
- **Threshold Source Needed:** Test protocol scenario pass criteria.

---

### 4.11 Final Relative Velocity (`final_relative_velocity`)
- **Mathematical Definition:**
  $$v_{\text{rel,final}} = v_{\text{ego}}[N-1] - v_{\text{target}}[N-1]$$
- **Unit:** meters per second (m/s)
- **Category:** Braking Effectiveness
- **Physical Meaning:** The residual speed difference between ego and target at the end of the test run.
- **Calculation in Software:** `samples[-1].relative_velocity`.
- **Distinction:**
  - *What We Measure:* Terminal velocity difference.
  - *What We Observed:* $\le 0.3$ m/s across all tested scenarios.
  - *What Constitutes Pass/Fail:* Must be $\le 0.0$ m/s to ensure target is pulling away or both vehicles are stationary.
- **Threshold Status:** **TBD**.
- **Threshold Source Needed:** Threat clearance criteria.

---

### 4.12 Minimum Relative Velocity (`min_relative_velocity`)
- **Mathematical Definition:**
  $$v_{\text{rel,min}} = \min_{k \in [0, N-1]} (v_{\text{ego}}[k] - v_{\text{target}}[k])$$
- **Unit:** meters per second (m/s)
- **Category:** Braking Effectiveness
- **Physical Meaning:** The maximum opening velocity achieved between vehicles (negative relative velocity indicates distance is increasing).
- **Calculation in Software:** `min(s.relative_velocity for s in samples)`.
- **Distinction:**
  - *What We Measure:* Peak opening speed.
  - *What We Observed:* Negative values during strong braking, confirming separation expansion.
  - *What Constitutes Pass/Fail:* Informational metric; negative peak confirms divergence.
- **Threshold Status:** **TBD** (Informational).
- **Threshold Source Needed:** Engineering design assumption.

---

### 4.13 FSM State-Transition Count (`state_transition_count`)
- **Mathematical Definition:**
  $$N_{\text{trans}} = \sum_{k=0}^{N-2} \mathbb{I}(s_k \neq s_{k+1})$$
- **Unit:** Integer count
- **Category:** Controller Stability
- **Physical Meaning:** Total number of discrete state switches executed by the FSM controller logic.
- **Calculation in Software:** Computed by `count_fsm_state_transitions(result)` by iterating through `aeb_state` samples.
- **Distinction:**
  - *What We Measure:* Count of state changes.
  - *What We Observed:* $17\text{--}24$ in nominal zero-noise runs; escalating to $35\text{--}61$ under noise ($\sigma = 0.20$ m).
  - *What Constitutes Pass/Fail:* Excess transitions degrade actuator life and create ride discomfort; upper bound must be established based on minimum dwell and actuator cycling limits.
- **Threshold Status:** **TBD**.
- **Threshold Source Needed:** Controller stability guidelines & Actuator cycling durability limits.

---

### 4.14 Triplet Reversal Count (`triplet_reversal_count`)
- **Mathematical Definition:**
  $$N_{\text{rev}} = \sum_{i=0}^{N-3} \mathbb{I}(s_i \neq s_{i+1} \land s_i = s_{i+2}) \quad \text{excluding } s_i = \text{"SAFE"} \land s_{i+2} = \text{"SAFE"}$$
- **Unit:** Integer count
- **Category:** Controller Stability
- **Physical Meaning:** **Number of 3-sample sliding FSM reversal patterns**. Measures the frequency with which the discrete FSM switches across a boundary and reverses back to the initial state within a 2-step window ($0.10$ s).
- **Calculation in Software:** Evaluated by `count_triplet_reversal_patterns(result)`. Matches the exact sliding window detector of `check_boundary_chattering()`.
- **Distinction:**
  - *What We Measure:* Sliding-window structural pattern matches in the discrete state sequence.
  - *What We Observed:* Baseline inflection count is $1\text{--}2$ in clean simulations (due to deceleration turnaround point $L2 \to L3 \to L2$); scales to $5\text{--}8$ (up to $11$) under noise ($\sigma=0.20$ m).
  - *What Constitutes Pass/Fail:* Must be limited via hysteresis and dwell time to prevent threshold hunting under noisy sensor inputs.
  - **Important Clarification:** This metric is **not** mechanical chattering, **not** physical vehicle vibration, and **not** an unsafe event indicator.
- **Threshold Status:** **TBD**.
- **Threshold Source Needed:** Software robustness limits & FSM hysteresis design requirements.

## 5. Current Evaluation Gaps (Pre-HIL Requirements)

To transition from pure Python software sensitivity analysis to physical **dSPACE Hardware-in-the-Loop (HIL)** validation, the following engineering gaps must be formally resolved:

1. **Literature-Supported Performance Criteria:**
   - Establishing validated minimum Time-To-Collision intervention thresholds based on human driver reaction times (e.g., Campbell et al., ISO 22839).
   - Documenting driver take-over time budgets for the acoustic/visual `WARNING` state.

2. **Platform & Vehicle-Specific Limits:**
   - Physical vehicle mass, center of gravity, and suspension pitch dynamics during emergency braking.
   - Maximum sustainable tire-road adhesion limits on dry asphalt ($\mu \approx 0.8\text{--}0.9$) versus wet/low-friction surfaces.
   - Exact hydraulic braking pressure limits and caliper clamping force capabilities.

3. **Justified Braking Deceleration Levels:**
   - Formal justification of multi-stage deceleration steps (currently $-2.0$, $-4.0$, $-6.0$ m/s²).
   - Assessing passenger restraint limits and cabin safety under $-6.0$ m/s² deceleration.

4. **Sensor Timing & Noise Characterization:**
   - Real sensor specifications (radar / camera) replacing idealized Gaussian sensitivity parameters.
   - Characterization of radar range resolution, false-target probability, and object classification latency.

5. **Actuator Bandwidth & Lag Justification:**
   - Experimental frequency-response data from the actual braking unit to validate the first-order lag model ($\tau$) and slew-rate limits.

6. **HIL Real-Time Criteria:**
   - Hardware clock synchronization, CAN bus baud rate ($500$ kbps / CAN FD), message cyclic timing ($20\text{--}50$ ms), and bus-load latency jitter.

7. **Standardized Test Protocol Alignment:**
   - Mapping scenarios directly to UNECE Regulation 152 and Euro NCAP AEB Car-to-Car test matrices (CCR stationary at 10–60 km/h, CCRm at 30–80 km/h, CCRb at 50 km/h).

## 6. Software-to-HIL Evaluation Continuity

To ensure complete continuity when progressing from Python software simulation to real-time dSPACE HIL testing, **the exact same 14 metrics will be computed on HIL telemetry**:

```
[ Simulation Telemetry ]  --> [ PerformanceEvaluator ]  --> [ Evaluation Report ]
                                      ^
                                      | (Identical Formulas)
[ dSPACE HIL CAN / RTI ]  --> [ HIL Telemetry Parser ]  --+
```

### Signal Mapping Table: Simulation to dSPACE HIL

| Metric | Python Simulation Source | dSPACE HIL Acquisition Channel | HIL Processing Method |
| :--- | :--- | :--- | :--- |
| **`collision_status`** | `s.raw_distance <= 0.0` | Real-time virtual environment contact sensor / CAN radar message | Synchronized HIL world model collision flag |
| **`minimum_distance`** | `min(s.distance)` | High-precision CAN distance signal (Radar/LiDAR ground truth) | Windowed minimum over scenario duration |
| **`aeb_activation_time`** | First `s.desired_deceleration < 0` | CAN message `AEB_Status` transitioning from `STANDBY` to `ACTIVE` | Timestamp difference relative to scenario start trigger |
| **`ttc_at_activation`** | $d / v_{\text{rel}}$ at $t_{\text{act}}$ | Computed from CAN range and range-rate signals at activation | Sampled at `AEB_Active` rising edge |
| **`max_actual_deceleration`**| `min(s.actual_deceleration)` | Vehicle IMU accelerometer CAN broadcast / dSPACE analog sensor | Calibrated low-pass filtered longitudinal acceleration |
| **`ninety_percent_braking_response_time`** | Time to 90% build-up | Pressure transducer in brake hydraulic line / ESC CAN pressure feedback | Timestamp difference: from ECU command to 90% line pressure |
| **`stopping_distance`** | Numerical integration of speed | Vehicle wheel-speed sensors (ESC CAN) / DGPS ground truth | Trapezoidal integration of calibrated ground speed |
| **`state_transition_count`**| Discrete changes in `aeb_state` | CAN message `AEB_State` byte | Event-counter of state changes on CAN bus |
| **`triplet_reversal_count`**| Sliding 3-sample detector | Sampled discrete `AEB_State` from ECU CAN log | Identical algorithmic detector applied to recorded CAN state trace |

By enforcing identical mathematical definitions and parsing pipelines, **HIL experimental traces can be benchmarked directly against software baseline curves** using the tables, percentiles, and classification criteria established in this framework.
